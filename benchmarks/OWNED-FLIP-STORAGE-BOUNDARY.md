# Owned vertical-flip storage boundary

An untimed audit finds a concrete reuse difference, **not a measured speedup**.
After the original two-live-result validation, managed repeated flips alternate
two backing arrays: **1,0,1,0,1,0,1,0**, on both OSes and both original depths.
An instrumented copy of the original native word worker reuses one output address
for its next eight operations after 16,384 warm operations. The frozen reference
binary is unchanged. Every instrumented clock is discarded.

Both operations materialize independent owned pixels and release them within the
operation. No missing native copy was found. FFmpeg retains its graph/frame
wrappers and padded rows; managed results have a new public owner and packed rows.
Those disclosed boundaries remain. This audit establishes neither equivalent
one-shot preparation nor a general allocator, cache, parser or performance claim.

The managed probe calls the original public flips, reproduces the original
validation disposal order and observes actual backing identities with untimed
reflection. Both frozen input hashes, every output sample, independent live
results and untouched sources pass. The live source is **531,468 / 1,062,936 B**;
idle result payload is **1,062,936 / 2,125,872 B** for byte/word cases. There are
no retained caller results at observation. These are ownership capacities,
distinct from total allocations and unmeasured physical/cache/native/JIT peaks.

The native diagnostic adds only a fixed **131,200 B static address recorder**
after materialization. It adds no dynamic allocation, formatting or I/O to
`apply`; addresses are emitted after all operations. All 16,396 identities remain,
including setup, warmup and the final check. Original two-live-output, complete
pixels and unchanged-input checks pass. One small managed probe and one diagnostic
native worker were built; no production, existing harness or baseline rebuild.
Two native preparation failures (return anchor, then pinned pkg-config path)
preceded any native build/operation; only pending preparation resumed.

Next hypothesis: prioritize recently returned image storage **within the existing
retained set and admission/replacement policy**. Keep slots, the 4 MiB ceiling,
duplicate/live-owner protection, `Return`/`ReturnLatest` behavior and caller-root
bypass. Add no pool, cache, API or kernel. Test an isolated complete word-flip
screen, then independently confirm only a credible gain. Reconcile affected
default-storage costs before any promotion or broad/package qualification.
Recency alone establishes no reduction in retained capacity or allocation.
